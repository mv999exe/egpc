# الشرح التقني — المشروع اتبنى إزاي وليه

مستند تقني تفهم منه المعمارية، آلية الضغط، سبب اختيار كل تقنية/مكتبة،
والإمكانيات اللي في إيدنا. (عربي + مصطلحات إنجليزي)

---

## 1) نظرة عامة على المعمارية

المشروع **static site** بالكامل — يعني HTML + CSS + JavaScript عادي (Vanilla)،
**من غير أي backend / سيرفر / build step / framework**.

```
egpc/
├── index.html            # الصفحة الرئيسية (8 كروت)
├── compressor.html       # صفحة ضغط الصور
├── css/styles.css        # ثيم أبيض/أسود مشترك
├── js/
│   ├── home.js           # منطق كروت "Coming soon"
│   └── compressor.js     # كل منطق الضغط + السلايدر  ← الملف المهم
├── vendor/
│   └── browser-image-compression.js   # مكتبة الضغط (مثبتة محليًا)
├── docs/                 # المستندات
└── .github/workflows/deploy-pages.yml # نشر تلقائي على GitHub Pages
```

**ليه Vanilla JS من غير framework؟**
- المشروع صغير ومحدود النطاق — React/Vue هيبقوا over-engineering ويكبّروا الحجم بلا داعي.
- بيشتغل من أي مكان بفتح `index.html` مباشرة، من غير `npm install` ولا bundler.
- الكود قليل ومباشر، فسهل قراءته ومراجعته وصيانته.

**ليه كل حاجة client-side (في المتصفح)؟**
- الضغط بيحصل على جهاز المستخدم → **صفر تكلفة سيرفر** و**خصوصية** (الصورة مبتترفعش).
- بيثبت السيناريو الأقوى: نضغط الصورة **قبل** ما ترفع، فنوفّر bandwidth الرفع كمان.

## 2) آلية الضغط — الأساسيات (الأهم)

### أ) إزاي أي ضغط صور في المتصفح بيشتغل أصلاً؟
الأساس هو **Canvas API**:
1. نقرأ ملف الصورة (`File`/`Blob`) ونعمله decode لصورة (`Image` / `ImageBitmap`).
2. نرسمها على `<canvas>` بـ `drawImage` — وهنا نقدر **نصغّر الأبعاد** (نرسمها بحجم أقل).
3. نطلّع الناتج بصيغة مضغوطة عبر `canvas.toBlob(type, quality)` — والمتصفح نفسه
   بيعمل الترميز (encoding) بمُرمِّزه الداخلي (مثلاً libwebp جوّه Chromium).

يعني **المُرمِّز الفعلي هو المتصفح**. المكتبة اللي بنستخدمها بتنظّم العملية دي
(تصغير + جودة + تكرار + EXIF + worker) لكن الترميز نفسه native → **سريع وخفيف**.

### ب) اللي مكتبة `browser-image-compression` بتضيفه فوق ده
- **Web Worker:** بتعمل الضغط في thread منفصل (عبر OffscreenCanvas) → الصفحة
  مبتعلّقش والواجهة بتفضل تستجيب.
- **حلقة استهداف الحجم (`maxSizeMB`):** بتفضل تنزّل الجودة و/أو تصغّر الأبعاد
  وتعيد الترميز **لحد ما توصل الحجم المطلوب** — ده اللي بيدينا "أصغر من كذا" مضمون.
- **معالجة EXIF orientation:** بتظبط دوران الصور من الموبايل.
- **تطبيع الصيغ:** jpeg/png/webp/bmp.

### ج) الإعدادات اللي اخترناها (في `js/compressor.js`)
```js
var PRESET = { maxWidthOrHeight: 1600, quality: 0.75, targetRatio: 0.5 };

imageCompression(file, {
  maxSizeMB: Math.max(0.02, sizeMB * PRESET.targetRatio), // هدف: نص حجم الأصل
  maxWidthOrHeight: PRESET.maxWidthOrHeight,               // سقف الأبعاد
  initialQuality: PRESET.quality,                          // جودة WebP الابتدائية
  useWebWorker: true,
  fileType: "image/webp",
});
```
**التلات روافع اللي بنتحكم فيها:**
1. **`maxWidthOrHeight` (الأبعاد):** أكبر مصدر توفير. صور الموبايل 3000–4000px،
   والمستند يتقري تمام عند ~1600px.
2. **`initialQuality` (الجودة):** بتشيل تفاصيل WebP اللي العين مبتلاحظهاش.
3. **`maxSizeMB` (هدف الحجم):** بيخلي المكتبة تكرّر لحد ما توصل حجم مستهدف.

### د) الضمانات اللي أضفناها بنفسنا (منطق في `compressBest` + `handleFile`)
- **تصغير مضمون حتى للصور الصغيرة:** لو الصورة أصلاً < 1600px، تصغير الأبعاد
  لوحده مبيكفيش، فبنستخدم `maxSizeMB` (نص الحجم) اللي بيجبر المكتبة تنزّل الجودة
  **والأبعاد** لحد ما توصل الهدف. وفيه **محاولة تانية أقوى** (1200px + quality 0.6)
  للحالات النادرة جدًا.
- **مستحيل الناتج يكبر عن الأصل:** بنقارن `best.size` بـ `file.size` وناخد الأصغر؛
  لو استحال نصغّر (صورة محسّنة تمامًا) بنرجّع الأصل.

الكود ده مبني ليكون سهل التعديل — لو عايز ضغط أقوى، غيّر `targetRatio` أو `quality`
أو `maxWidthOrHeight` في متغير `PRESET` واحد بس.

## 3) ليه صيغة WebP؟ (وليه مش غيرها)

| الصيغة | الحجم | التوافق (كملف منزّل) | الترميز في المتصفح | القرار |
|---|---|---|---|---|
| **JPEG** | مرجع | عالمي 100% | مدعوم | احتياطي فقط |
| **WebP** | أصغر 25–35% من JPEG | كل الأجهزة الحديثة | مدعوم native | ✅ **المختار** |
| **AVIF** | أصغر 20–50% من WebP | أقل (أجهزة/تطبيقات قديمة) | **غير مدعوم** موثوق في Canvas | ❌ مستبعد |
| **PNG** | كبير (lossless) | عالمي | مدعوم | مش مناسب للضغط |

**تقنيًا:** WebP اللوسي مبني على **VP8 intra-frame coding** (تنبؤ بلوكات + تحويل
تردّدي + ترميز حسابي) — أكفأ من الـ baseline DCT + Huffman بتاع JPEG. وبيدعم
chroma subsampling ودرجات جودة 0–100.

**ليه مش AVIF مع إنه أصغر؟**
- `canvas.toBlob('image/avif')` **مش مدعوم بشكل موثوق** في كل المتصفحات (Safari/Firefox)
  → كنّا هنحتاج **WASM encoder** (ثقيل، أبطأ).
- وكملف منزّل، AVIF مش مضمون يفتح على الأجهزة/التطبيقات القديمة → بيكسر شرط
  "تشتغل في أي مكان". فاخترنا WebP كأفضل توازن **حجم × توافق**.

## 4) ليه المكتبة دي؟ (`browser-image-compression`) وليه مش غيرها

| الخيار | المميزات | العيوب | ليه أخدناه/سبناه |
|---|---|---|---|
| **browser-image-compression** ✅ | Web Worker، حلقة `maxSizeMB`، EXIF، WebP، MIT، ~57KB | المُرمِّز = بتاع المتصفح (مش الأقصى نظريًا) | **الأنسب**: تحكم كامل + خفيفة + مجانية |
| Canvas يدوي (من غير مكتبة) | صفر dependency | نعيد كتابة: resize + حلقة الحجم + EXIF + worker | مجهود بلا داعي |
| compressorjs | بسيطة، canvas-based | تحكم أقل في **هدف الحجم** (مفيش حلقة maxSizeMB بنفس القوة) | تحكم أقل |
| WASM codecs (Squoosh / @jsquash) | أقصى جودة + يدعم AVIF | **تحميل ثقيل** (WASM)، أبطأ، أعقد | overkill لـ PoC |
| Server-side (`sharp`/libvips، Pillow) | الأقوى والأثبت، batch، أي صيغة | محتاج CPU + infra على السيرفر | خيار الـ production (قسم 6) |

**الخلاصة:** لـ PoC في المتصفح، `browser-image-compression` بتدينا أقصى تحكم
(جودة/أبعاد/هدف حجم) بأقل تعقيد وأصغر حجم وصفر تكلفة — وده اللي محتاجينه دلوقتي.

## 5) تقنية سلايدر before/after (من غير أي مكتبة)

فكرة بسيطة بالكامل CSS + JS:
- طبقتين صور فوق بعض جوّه `.compare`:
  - **الأساس (تحت):** الصورة "بعد" (`.after-layer`) بعرض 100%.
  - **الطبقة الفوق:** الصورة "قبل" جوّه `div` عليه `overflow: hidden`، وعرضه =
    نسبة موضع الخط. لما بنغيّر عرض الـ div بنكشف/نخفي جزء من صورة "قبل".
- **الخط (`.divider`)** بنحرّكه بـ **Pointer/Touch events** ونحسب النسبة من
  `getBoundingClientRect`. الكود في `js/compressor.js` (`setDivider`, `startDrag`).
- الصورتين بتتعرضوا بنفس العرض، فالمقارنة دقيقة حتى لو دقتهم الأصلية مختلفة.

## 6) التطبيق في production — إيه اللي عندنا

نفس الفكرة تتنفّذ في مكانين، والكود الحالي بيثبت الأول:

**أ) Client-side (زي الديمو):** نضغط في متصفح المستخدم بنفس المكتبة قبل الرفع.
- الأفضل: توفير bandwidth الرفع + التخزين، وصفر حمل على السيرفر.
- بنربطه بـ `<input type=file>`: نضغط الـ `File` ونرفع الناتج بدل الأصل.

**ب) Server-side:** المستخدم يرفع عادي، والسيرفر يضغط قبل الحفظ.
- بمكتبة **`sharp`** (Node.js، مبنية على libvips — سريعة جدًا) أو **Pillow** (Python).
- تحكم مركزي وثابت، مستقل عن جهاز المستخدم، لكن بيستهلك CPU.

**قرارات production:**
- نحتفظ بالأصل + نسخة مضغوطة للعرض، ولا نستبدل؟ (الأفضل: الاتنين).
- الجودة/الأبعاد المستهدفة حسب نوع المحتوى (فواتير محتاجة وضوح أعلى).
- strip metadata (EXIF) لتوفير أكتر وخصوصية.

## 8) القوة اللي في إيدنا (الإمكانيات)

الروافع اللي نقدر نتحكم فيها أو نوسّعها بسهولة:

- **الجودة (`initialQuality`)** — نوازن بين وضوح وحجم لكل نوع محتوى.
- **الأبعاد (`maxWidthOrHeight`)** — أقوى رافعة توفير.
- **هدف الحجم (`maxSizeMB`)** — نضمن "أصغر من كذا".
- **الصيغة (`fileType`)** — WebP دلوقتي، ونقدر نضيف **JPEG fallback** لتوافق 100%.
- **Presets** — نضيف مستويات (أعلى جودة / متوازن / أصغر حجم) يختارها المستخدم.
- **Batch** — نضغط أكتر من صورة مرة واحدة.
- **client أو server** — نفس الفكرة في الاتنين.
- **الاحتفاظ بالأصل** أو استبداله، وتخزين نسخ متعددة (thumbnail/preview/original).
- **strip metadata** لخصوصية وتوفير.
- **Web Worker** — كل ده من غير ما نعلّق واجهة المستخدم.

**الخلاصة التقنية:** عندنا pipeline ضغط كامل client-side، متحكَّم فيه بالكامل،
مجاني، خفيف، ويشتغل offline — وقابل للتوسّع لـ server-side أو presets أو batch
بأقل مجهود، لأن كل المنطق متركّز ومنظّم في `js/compressor.js`.
